# TypeScript, SQL, and Code Conventions

## TypeScript

- The project uses `strict: true`, `module: NodeNext`, and `target: ES2022`.
- Relative imports must include the `.js` extension, even when importing a `.ts` file.
- Prefer `import type` for type-only imports, matching the existing server code.
- Keep shared domain shapes in `src/types.ts`. Map external payloads (JSON, proto, Kafka) into domain types at the boundary.
- Do not edit `src/gen/`; it is generated by `buf`.
- `src/lib/fplib/` is a standalone pure-TypeScript functional toolkit (Either, Monoid, pipe/compose, curry, match, branded types). It must stay free of Node/Web globals, and it is not currently imported by the server. Use it only when the abstraction clearly improves the code.

## Formatting

- Use 2-space indentation.
- Server code uses semicolons and double quotes; match the surrounding file when a file deliberately differs.
- Keep modules focused on one responsibility.
- Comments should explain invariants, tradeoffs, or non-obvious behavior, not restate the code. Application code is terse; the `fplib` files are heavily documented by design.

## SQL and database access

- Use postgres.js tagged templates for values: `sql\`... WHERE id = ${id}\``.
- Use `sql.identifier(...)` for dynamic identifiers such as view names.
- Never concatenate untrusted input into SQL strings.
- Only `metrics_1m`, `metrics_1h`, and `metrics_1d` are valid aggregate view names.
- Store timestamps in UTC. `MetricsFlusher` converts `Date` values to ISO strings before inserting.
- For a list of ids, bind the array as a value (`WHERE id = ANY(${ids})`) — postgres.js renders it as a Postgres array — instead of joining ids into the query string. Validate the count server-side (compare allows 2–10).
- Treat `src/db/schema.sql` as the source of truth for the schema; keep it consistent with the types and queries.

## Query parameter validation

- Parse and bound every query parameter in the route before touching the database: `limit` (1–100), `offset` (≥ 0), `interval_ms` (100–60000), and `granularity` (allow-list). Return `400` with a stable `{ error: "…" }` body instead of letting the database reject it or silently clamping.
- `undefined` means "not supplied" (use the default); an empty string is a supplied, invalid value and should fail validation.
- Keep one helper per concern: `parseGranularity`, `parseIntParam`, `parseCompareIds`. A static path such as `/compare` must be registered before `/:id` so it is not captured as a run id.

## Ingestion and error handling

- JSON ingestion goes through `normalizePoint` / `normalizeBatch`, which tolerate snake_case and camelCase aliases.
- Every ingestion path must call `metricsFlusher.ingest`; the flusher owns buffering, batching, retry, and drop accounting.
- Do not block an ingest path on a database write.
- Kafka is disabled unless `KAFKA_BROKERS` is set; keep the disabled path silent and safe.
- Artillery reports are another ingestion boundary: `parseReportPoints` converts them to `MetricPoint[]`, and `processReport` calls `metricsFlusher.ingest` rather than inserting directly.
- Accept both `period` and `timestamp` report keys and both `histograms` and `summaries`; older and newer Artillery releases differ. Treat missing plugin data as aggregate-only, not an error.
- Aggregate rows use `endpoint: ""`. Per-endpoint rows use plugin keys under `plugins.metrics-by-endpoint` (or a custom `metricsNamespace`); do not invent a `custom` report field.
- Guard run lifecycle handlers with `settled`/`killed` flags so `close` and `error` cannot process a run twice or ingest a partial report.
- Log operational failures with a stable prefix such as `[flusher]`, `[kafka]`, `[artillery]`, or `[server]`.

## Configuration

- Read environment variables only in `src/config.ts`.
- Add new variables to `.env.example` and document them in the README configuration table.
- Never commit `.env` or secrets.

## Logging

- Use the shared Pino logger from `src/logger.ts`; do not use `console.*` in server code.
- Pass errors as `{ err }` so Pino serializes them: `logger.error({ err }, "message")`.
- Request logging is handled by `@hono/structured-logger` in `src/server/app.ts`.

## Quality gates

- Tests use Vitest and Hono's `testClient`. Run `pnpm test` or `pnpm test:coverage` before finishing changes. Keep coverage at or above the 80% gate.
- Before finishing a change, run `pnpm task lint` and, when protos or generated files are involved, `pnpm task proto:check`.
- Update the README when commands, configuration, API behavior, or architecture changes.
